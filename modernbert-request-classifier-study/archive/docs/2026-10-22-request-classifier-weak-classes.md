# 「その他の依頼」「周囲の観測」が弱い理由の調査（2026-10-22）

**訂正：[後続のユーザー指定](2026-10-22-request-classifier-scope-correction.md)を優先する。機能説明・翻訳・過去の話・弓への持ち替えを補う提案と、雑談・取消をother_requestへ置く前提を撤回した。以下は旧条件による調査記録。**

## 結論

**最も具体的に確認できた問題は、学習側で扱う内容の偏りと、内容の種類を考慮していない分割。分類境界と学習設定も影響している。** 総件数を増やすだけ、学習率を下げるだけで解消できるという結果ではない。

| 要因 | 確認した根拠 | 判断の限界 |
|---|---|---|
| 学習素材・分割 | 説明・翻訳・過去の話、地形名での確認・照明状態などがtrainにない。既知の型は一部正解、未学習の型で失敗 | 内容内訳は今回の事後監査。追加素材による改善量は未測定 |
| 分類境界・入力 | 依頼と独り言、説明と実行、一般モブと敵、現在観測と一般知識を混同。履歴なしでは参照対象が欠ける例もある | 本文だけで区別できる誤りも多い。全件を曖昧さで説明できない |
| 学習設定 | trainは対象2分類とも全問正解。後半の過適合と、学習率を変えた際のdevの変動を確認 | 単一seed。全体の改善は小さく、低学習率モデルにも偽陽性が多い |
| 実装の配線 | 11ラベル対応・入力・保存checkpoint・評価を照合。切り詰めなし | これらの範囲では誤配線は見つからなかった |

**ユーザー確認済みの意図を含む97件の基準例、全原文・ラベル・分割・既存採用モデルは変更していない。** 調査用CPUモデルは本体へ接続していない。

## 2. 「その他の依頼」：例の総数より内容が偏っている

| 元Colabでの正解 | train | dev | test |
|---|---:|---:|---:|
| その他の依頼 | 26/26 | 0/6 | 0/9 |
| 周囲の観測 | 13/13 | 2/5 | 1/5 |
| 全11分類 | 312/313 | 42/59 | 45/76 |

その他のtrain26件は、敵情報25件・剣23件と同程度。**件数の少なさだけでは、その他が全問外れる理由を説明しにくい。** 内訳は以下のように偏っている。

| その他の内容内訳 | train | dev | test |
|---|---:|---:|---:|
| 取消・待機・現在状態の維持 | 9 | 0 | 0 |
| 将来・条件成立時の操作 | 3 | 0 | 0 |
| 複数依頼 | 2 | 0 | 0 |
| 専用分類以外の動作・発話 | 8 | 5 | 1 |
| 行動相談・提案要求・自己への問い | 2 | 1 | 2 |
| 操作できるかの確認 | 1 | 0 | 0 |
| ドギドの所在 | 1 | 0 | 1 |
| 機能・使い方の説明 | **0** | 0 | **2** |
| 翻訳・言い換え | **0** | 0 | **2** |
| 過去の体験を話す依頼 | **0** | 0 | **1** |

trainの14/26件が取消・条件・複合依頼。同じ「その他」でも、testで問われる説明や翻訳の型が欠けている。train659の「松明に持ち替えられるか」は関連する可否確認であり、説明依頼の近隣例はあるが、十分な広がりはない。

具体的な失敗：

- **「弓に持ち替えて。」→剣**。弓への持ち替えの正例183・585が両方dev。trainに対象を弓へ替える正例がない。
- **「飼っている猫を呼んで。」→乗り物**。trainに犬の呼び寄せ588はあるが1件だけ。対象の種類をまたぐ一般化が弱い。
- **「馬の呼び戻し機能の使い方を教えて。」→剣**。手順説明の例はtest。単に文中の「馬」へ反応しただけでも説明できない誤り。
- **引用した台詞の英訳・関西弁への変更→依頼なし／剣**。操作の言及と、その操作の実行を分けられていない。
- **「冒険どこ行く？」→依頼なし**。ユーザーが確認した提案依頼の意図は維持する。
- **「あれ?ドキドどこ行ったん?」→依頼なし**。trainの「あれドギドどこ?」は正解。ここは内容の型が完全に欠けているわけではなく、表記・言い回しへの一般化も疑われる。表記だけが原因かは未実験。

逆方向にも、「斧じゃなくて剣にして。」や「剣は自分でやるからロバだけお願い」がその他へ流れる。取消を含む文と、別対象を否定して依頼を絞る文を区別する必要がある。取消例の存在自体を誤りとみなす根拠はない。

## 3. 「周囲の観測」：13件では観測の種類を覆えていない

| 観測の内容内訳 | train | dev | test |
|---|---:|---:|---:|
| 一般モブの位置 | 2 | 0 | 0 |
| 音 | 3 | 1 | 0 |
| 一般モブの数 | **1** | 0 | **2** |
| 今見える対象の報告 | 3 | 1 | 0 |
| 現在地・構造物の正体 | 3 | 0 | 1 |
| 匂い | 1 | 0 | 0 |
| 地形名を挙げた確認 | **0** | **3** | 0 |
| 観測情報を取得できているかの確認 | **0** | 0 | **1** |
| 現在の照明状態 | **0** | 0 | **1** |

- devの「砂漠かな」「砂浜かな」「海はあるかな」は全て依頼なし。3件が同一groupで、同種の正例がtrainにない。
- testの牛の頭数は敵情報へ流れた。trainの一般モブの数は「村人さん何人いるかな」1件だけ。
- 窓の明かりが今ついているかの問いはMinecraft一般知識へ流れた。照明状態の観測質問がtrainにない。
- 正解した「何の音?」「塔の周りには今何が見える？」「ここは何だ?」には、それぞれ音・視認・現在地というtrain側の対応例がある。

観測のdev5件はわずか2 group。3件の地形確認を別々の独立した失敗として数え過ぎない。1件の正誤だけで再現率は20ポイント動く。

## 4. 前回の選別と今回の分割で、代表例が学習側から抜けた

素材全体では、その他92→41件（40件を代表へ集約、境界保留4件、文脈必要7件）、観測26→23件（境界保留3件）。観測は大量の類似例を削って小さくした分類ではなく、もともとの数が少ない。

その他では、次の対応がある。

| 集約した旧例 | 残した代表 | 代表の分割 |
|---|---|---|
| 機能説明540 | 172 | test |
| 翻訳592・596・600・632 | 174 | test |
| 建築554・562 | contrast042 | dev |
| 弓への切り替え499 | 183 | dev |
| 敵を代わりに倒す508 | 182 | test |

**前回私が行った整理では、「代表が素材全体に残る」ことまでの確認にとどまり、「trainに独立した場面の例が残る」ことを確認できていなかった。** 分割はラベル件数・出典・総数とgroupの分離を調整したが、ラベル内の内容の広がりを扱っていなかった。

ただし、削る前後を同じ条件で学習した比較はしていないため、「削減によって何ポイント悪化した」とは言えない。今のdev/testの近似文をtrainへ戻して成績を上げる対応も適切でない。将来の素材では別場面から独立例を集め、内容の広がりを確認してから分割を固定する必要がある。

## 5. 境界はユーザー確認済み意図を基準に整理する

### 固定する基準

- 「冒険どこ行く？」「のんびり・・・というと具体的になにをする？」は**その他の依頼**。モデルに合わせて依頼なしや観測へ移さない。
- ユーザー追加例の「あれは何だ」は**視線の誘導**、「あそこにいるピンク色の生き物は何だ?」は**Minecraftの知識**として保持する。
- 「エンダーマンがいる」「生き物がいるぞ」などのユーザー確認済みの注意・視線誘導を、表面が報告文だから依頼なしとは扱わない。
- 「ええ？背中が平らではないって・・・・どんな姿？」は確認済みの**依頼なし**。聞き返しが疑問形でも、現在観測へ移さない。

「何」「いる」「かな」の有無だけで分類すると、この基準と衝突する。

### 未確認の境界で、素材の説明を揃える必要がある箇所

1. **提案依頼と独り言**：確認済み「冒険どこ行く？」と、trainの「どこ行こうかな」では、誰に何を求めているかが違う。自然な別例を保持する。
2. **ドギドの所在**：231・294は現在otherで、いずれも暫定解釈。世界観測や呼び寄せと何を区別するかを記録する。現ラベルは維持。
3. **「ストラクチャー情報見えてるでしょ」**：観測内容そのものと、情報の取得可否を確かめる発話の境界。確認権限はキュレーターの拡張分類解釈で、ユーザー確認とは区別する。
4. **指示対象が省略された問い**：履歴なしの現入力では、いま見た物への注意喚起、一般知識の質問、前の説明への聞き返しを区別しきれない場合がある。欠けた文脈を作らず、曖昧さを記録する。

一方、「弓へ」「牛は何頭」「今見えている窓の明かり」は本文に対象・問いがある。これらは境界を見直して正解を変える対象ではなく、今の基準をモデルが学ぶべき例。

## 6. 設定の切り分け：学習率だけを変えたCPU比較

既存trainerを使い、同じMac CPU・4 thread・基盤revision・seed43・313/59/76件・batch16・10 epochを固定。**5e-5と2e-5の2試行を事前に決めて実行**した。学習設定ファイルの差は学習率と出力先だけ。testを使った選択は行っていない。

元Colabも比較CPUも、Python・記録対象のパッケージの版は一致。GPUとCPUで数値計算が異なるため、学習率の効果はCPU同士で比較する。

| 試行 | 選択epoch | dev全体macro F1 | その他 正解/対象・F1 | 観測 正解/対象・F1 |
|---|---:|---:|---:|---:|
| 元Colab GPU・5e-5（参考） | 5 | 0.642215 | 0/6・0.000 | 2/5・0.571 |
| 同一CPU・5e-5 | 7 | 0.642339 | 2/6・0.364 | 3/5・0.600 |
| 同一CPU・2e-5 | 7 | 0.647042 | 4/6・0.500 | 3/5・0.750 |

低学習率ではその他のdev再現率が2/6→4/6へ改善。ただし適合率は両方40%で、その他と予測した数も5→10件へ増えた。観測の再現率は3/5のまま、適合率が60%→100%へ改善した。全体macro F1の差は約0.0047にとどまる。

元GPUの0/6→低学習率CPUの4/6を、学習率だけの効果として扱わない。同じ5e-5でもCPUはepoch7がepoch5を約0.00012上回り選択された。小さいdevでは僅差によって採用epochが変わる。

### 過適合とcheckpointの選択

元Colabは20 step/epoch、計200 step、選択はepoch5・100 step。最終epoch10を誤って採用したわけではない。

| 元Colab epoch | 学習中のtrain loss | dev loss | dev全体macro F1 |
|---|---:|---:|---:|
| 4 | 0.4954 | 1.2933 | 0.5570 |
| 5・選択 | 0.0921 | 1.9661 | 0.6422 |
| 6 | 0.0110 | 4.9739 | 0.6100 |
| 10 | 0.00000084 | 4.1856 | 0.5333 |

学習例はほぼ全て覚え、後半にはdev lossが悪化する。さらにCPUの5e-5では、観測はepoch4で4/5だが、全体の規則が選ぶepoch7では3/5。**全体macro F1の最大化と、各分類の最良epochは一致しない。** 今回から分類別のepoch指標を既存ログへ追加した。

full fine-tuning、AdamW、weight decay 0.01、warmup0、分類ヘッドdropout0、class weightingなし。これらは今後の候補だが、今回は学習率以外を同時に変えていない。勾配clipはmax_grad_norm1.0。インストール済みTrainerの実装でもclip前のnormをログに返しており、大きいログ値だけを根拠にclipなしの勾配暴走と断定しない。

### 選択した低学習率モデルの既存testへの結果

選択後に既存のtestを一度評価した。これはすでに誤りを見ている**診断用test**で、新しい独立評価ではない。

| 指標 | CPU・2e-5 |
|---|---:|
| 全体 | 42/76件、macro F1 0.461 |
| その他 | 3/9件、適合率30%、F1 0.316 |
| 観測 | 3/5件、適合率23.1%、F1 0.333 |

観測と予測した13件のうち正解は3件。再現率だけは上がっても、広く観測へ流す副作用がある。元Colabの全体45/76件・F1 0.523を上回っておらず、設定変更だけで解決した、または採用に進めるという結果ではない。GPUとCPUの差も含むため、この全体差を学習率の効果量にはしない。

## 7. 次に直す順序

1. **内容の不足を埋める。** その他は機能説明・翻訳・過去の話・自然な提案依頼・未対応対象/動作、観測は地形確認・一般モブの数・明かり等の現在状態。確認済み意図を軸に、別場面から自然な独立例を集める。
2. **選別・分割の確認項目を増やす。** 類似例の集約後、同じ分類の中に必要な内容と独立groupが残っているかを見る。類似文をtrain/testへ分けて見かけの点数を上げない。
3. **未確認の境界だけを明文化する。** 確認済み意図を動かさず、宛先・参照対象・現在観測か一般知識かを説明する。単文で分からないものを無理に確定しない。
4. **素材を固定してから設定を評価する。** 今回の低学習率は次の比較候補。複数seedや正則化・重み付けはそれぞれ分けてdevで検討し、最終判断には新しい場面の評価を用意する。

本調査では新規学習例の追加・既存ラベルの変更・再分割・本体採用は行っていない。
