# Geminiへの依頼文：ドギドの長文履歴を使う学習素材

Minecraftの相棒「ドギド」とユーザーの会話から、現在のユーザー発話の意図を5分類する、日本語の学習候補を作成してください。今回は短文単独の問題ではなく、実運用の長い会話履歴を踏まえて判断する素材が必要です。

# 今回の成果物

- 合成データ30件。5ラベルを各6件。完成したUTF-8のJSONLだけを出力してください。1行に1オブジェクト、全30行。Markdownの囲み、導入文、別の解説、集計文は付けません。
- idは `gemini_long_` の後に001から030までの3桁連番を付けてください。group_idは `gemini_long_20261015_` にグループを識別する小文字英数字・アンダースコアを付けてください。
- 実ログを直接渡していないため、sourceは全件 `synthetic`。実測、観測済み、再現ログと称さないでください。
- 下の条件だけから新しく作成してください。過去に作ったデータの本文、既存の問題集、他モデルの回答の言い換えは使いません。

# 参考にする実運用の会話構造

ドギドの記録では、ユーザーと交互に発話するだけでなく、周囲を見てドギドだけが続けて話す場面があります。移動で景色・音・見える対象が変わり、ユーザーは短く相槌を打ちます。質問を言い直す、対象や方角を訂正する、雑談を挟んで前の話題へ戻ることもあります。

通常の履歴は直近最大10発話で、各発話は最大80文字です。現在のユーザー発話はそれと別枠です。履歴を長くするための長大な独白や、同じ注意書きの反復は、この運用には合いません。

ドギドは日本語で自然に話す相棒です。一人称はオレ、軽い関西寄りの口調を基本にして構いません。ユーザーの話し方は固定しません。過剰な方言、すべてが同じ語尾になる会話、学習問題のような説明は避けてください。

# 分類するもの

履歴全体の話題ではなく、履歴を踏まえた「現在のユーザー発話で最後まで有効な意図」を1つ選びます。履歴の中の依頼や単語を見つけただけで、そのラベルを選ばないでください。

| label | 定義 |
|---|---|
| not_request | 挨拶、感想、感情、報告、自分で行う予定、単なる引用や回想など。現在の質問・依頼・禁止・取消はない。 |
| enemy_information | 現在の敵の有無、位置、方角、距離、数、見えるかを尋ねる依頼。 |
| equip_sword | ユーザー本人の手持ちを、剣へ持ち替える現在の依頼。承諾や文脈で明確な間接依頼も含む。 |
| recall_mount | いま、乗れる動物をユーザーのところへ呼び出す依頼。文脈で明確な騎乗希望や承諾も含む。 |
| other_request | 上記3種類の専用依頼に当たらない質問・依頼、禁止・取消、将来の実行予約、依頼の分類先が解消できない参照、独立した複数の有効な依頼。 |

# 分類の境界と機能の範囲

1. 現在の明示的な依頼は、履歴に回想・引用・実行完了があっても消えません。一方、現在発話が完了への了解に留まる場合は、新たな操作を作らないでください。未実行の提案への承諾と、実行後の了解を区別します。
2. 言い直しや取消がある場合は、最後に残る依頼を判断します。禁止や取消だけの発話はother_requestです。依頼を実行した後の感謝はnot_requestになり得ます。
3. enemy_informationは現在の敵に関する上記項目に限定します。敵という話題を含む知識質問、過去記録、攻撃の依頼、ユーザー本人の位置、敵とされていない動物の位置は同じラベルではありません。中立の動物を敵として扱うなら、現在その敵対性が会話で分かる必要があります。
4. equip_swordはユーザーの手持ちを剣へ替える機能です。物品の運搬、受け渡し、収納、製作、剣の使用法の説明を同じ操作として扱いません。
5. recall_mountの対象種は、馬、ロバ、ラバ、スケルトンホース、ゾンビホース、ラクダ、キャメルハスク、ブタ、ストライダー、ハッピーガスト、オウムガイ、ゾンビオウムガイ、ラマ、商人のラマです。犬・猫・ボート・ドギド自身は含みません。動物の名前だけでは種類を推測せず、必要な対応を履歴に置いてください。所有・候補の現在性・呼び出し可能性は実行側が別途確認するため、呼び出し意図が明確なら、それらが未確認というだけでother_requestへ落としません。
6. 現在の条件を確かめて答える質問と、未成立の将来条件で自動実行する予約を区別します。後者はother_requestです。
7. 相手への間接的な依頼と、自分の感想・自己行動の予定を、文脈から区別してください。依頼か否かそのものを判断できない素材は作り直し、都合よくother_requestへ入れないでください。
8. 動詞や疑問文の個数ではなく、独立して有効な依頼の数を見ます。理由として述べた事実、取り消した依頼、本人が行う行動を追加の依頼として数えません。別々の操作や情報要求が同時に残る場合はother_requestです。
9. 未対応の要求をユーザーがする素材はother_requestとして作成できます。ただし、assistantに未対応操作を実行・成功・約束させないでください。見えていない所持品や遠方の状態、記録にない過去の出来事を、相棒が当然知っているように断定することも避けます。ユーザーが話した情報を受け止めることはできます。
10. 今回は通常会話です。進行中の句作り・読み上げ練習など、別の専用対話状態が受け持つ発話は混ぜないでください。再開だけでなく、その作業内の感想・採否・続行も含みます。通常会話での一般的な質問・報告まで、話題の単語だけで除外する必要はありません。
11. 表記の揺れを入れるなら少数にします。この分類仕様では県は剣として扱います。ただしその揺れをラベルの目印にしたり、無理に全ラベルへ配置したりしないでください。

# 長い履歴の作り方

- 各件のcontextは古い順に8〜10発話。各発話は80文字以内。現在発話はcontextに重複して入れません。各行だけで判断できるようにし、同じgroupの別の行の内容を暗黙の履歴として借りないでください。自然に短い相槌を含めてよく、文字数を埋めるための発話は不要です。
- 30件全体で少なくとも18種類の異なる履歴を作ってください。同一履歴の再利用は最大3件までにします。名前や語尾だけを替えた履歴で種類数を満たさないでください。
- assistantだけが観察を続けた履歴を6件以上、userとassistantの会話を含む履歴を18件以上にします。交互発話を強制せず、同じ話者の連続発話も自然に使います。
- 現在発話を完全に同じに保ち、履歴の意味の違いで正解が変わる対照を6組、計12件入れてください。対照の各組は同じgroup_idにまとめます。実際には正解が変わらない対照を無理に作ってはいけません。
- 上記対照のうち3組、計6件では、履歴の冒頭側に必要な参照を置き、末尾4発話を両側で同じにしてください。その末尾4発話で対象・行為・正解を言い直さず、冒頭を読まないと区別できない設計にします。単なる名前の差だけでラベルを変えず、種類・行為・状態など意味上の根拠を変えます。
- 履歴に別の話題があっても、現在発話の新しい明確な依頼をそのまま分類する素材も8件以上入れます。すべてを遠い参照の問題にしないでください。
- 背景描写、短い相槌、訂正、話題の中断と復帰、未実行・完了の違いなどを分散させます。全件を同じ会話順序や同じ接続表現で作らないでください。
- 履歴に分類ラベル、採点者向けの説明、判断規則、実装手順、隠れた状態の注釈を入れません。確認や完了報告は、登場人物の自然な発話として必要なときだけ使ってください。
- 同じ履歴から派生した素材、意味の近い対照、言い換えは同じgroup_idにまとめてください。後で学習用と評価用へ分割するとき、同じ会話由来の素材を別側へ漏らさないためです。

# JSONLの必須フィールド

各行は次の9フィールドのみです。具体的な会話例やJSON完成例は提示しません。

| フィールド | 型・条件 |
|---|---|
| id | 重複しない文字列。冒頭の形式に従う。 |
| group_id | 共通の会話・対照・言い換えを束ねる文字列。冒頭の形式に従う。 |
| text | 現在のユーザー発話。空でない日本語文字列。 |
| context | 発話オブジェクトの配列。各要素のキーはroleとtextのみ。roleはuserまたはassistant、textは空でない自然な発話。 |
| label | 上記5ラベルのいずれか1つ。 |
| needs_clarification | JSONのboolean。後述の条件と一致させる。 |
| tags | 後述の許可語彙から、実際に該当するものを選ぶ重複なしの非空配列。全件にcontextを付ける。 |
| source | synthetic固定。 |
| rationale | 正解を支える現在発話・履歴の意味を短く記した日本語文字列。入力にない前提を足さない。モデルへ渡す会話本文とは別の注釈。 |

使用可能なtagsは、ambiguous, cancellation, casual, context, correction, count, direct, ellipsis, future, general_knowledge, hypothetical, iruka_collision, location, multiple_requests, named_entity, negation, orthography, past, politeness, presence, quotation, question, reference, reported_speech, rhetorical, self_location, statement, unsupported_request です。独自タグを追加しません。

needs_clarificationは、tagsにambiguousまたはmultiple_requestsがあるときだけtrue、それ以外はfalseです。その2タグを使う行のlabelはother_requestにします。参照が履歴から解けるだけの省略はambiguousにしません。unsupported_requestを付ける場合もlabelはother_requestです。未対応であることと意味が曖昧であることは別なので、それだけでneeds_clarificationをtrueにしません。
